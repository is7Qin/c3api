# Changelog

All notable changes to c3api are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versioning follows the policy below.

## Versioning

During the **beta** phase, versions are `v0.x.0-beta.N` (N increments with each release). The first beta is `v0.0.1-beta.1`; concrete numbers for later releases are decided at tag time.

## [Unreleased]

### Breaking

- **The overview account-status split is redefined into two axes and three buckets, and `accounts.disabled` has reversed meaning**: `GET /api/admin/overview`'s `accounts` object no longer carries `unhealthy` and `429` (both were permanently zero — the backing `StatusUnhealthy` / `Status429` states have no producer) and gains `failed`. `active` / `failed` / `disabled` are now an exhaustive, mutually exclusive split of the routable (assigned-to-a-group) account pool along the two real axes — manual enable/disable (`enabled`) and runtime failure (`failed_at`): `disabled` = manually disabled (`enabled = false`), `failed` = enabled but runtime-failed (`failed_at` set), `active` = the rest; the three always sum to the number of grouped accounts. **`disabled` is a same-name semantic reversal**: it previously counted runtime-failed accounts (what `failed` now counts) and now counts manually-disabled ones, so any out-of-repo admin client that reads `disabled` silently receives the opposite meaning. Only the dashboard consumes this object in-repo and is updated in the same change; manually-disabled accounts were previously miscounted as `active`. The cards read from the scheduler snapshot and remain subject to the endpoint's internal 30s cache plus the dashboard's 30s poll (~60s worst-case convergence).

## [v0.0.1-beta.8] - 2026-10-12

### Breaking

- **The static admin token is gone; `/api/admin` is `platform_admin`-only**: the `admin.token` config key and the `C3API_ADMIN_TOKEN` environment variable are removed, the Helm chart no longer renders an `admin-token` secret key or injects it, and `.env.example` / `compose.yml` / the shipped config templates and docs no longer carry it. A config or deployment still setting the key now fails at startup (unknown key), so upgrades must drop `admin.token` from `config.toml` / `deploy/config.toml` / `compose.yml` and `secrets.adminToken` from Helm values. The admin surface now accepts exactly two credentials, both of which must resolve to a `platform_admin` identity: a `platform_admin` JWT (the snapshot role overrides the claim) or a platform_admin-owned management API key (see below). Missing or empty credentials are rejected (deny-by-default). Because both surviving paths inject the operator's user id, a redemption code's `created_by` is now always the acting platform_admin; previously the static-token path recorded `created_by = 0` ("system").

- **`usage_logs` partition retirement is now gated on unsettled funds (behaviour change, every deployment)**: the retention worker no longer drops a daily partition purely by date. In one `ACCESS EXCLUSIVE` transaction it first inspects the partition for uncredited earning rows (`NOT supplier_credited AND supplier_earn_millis > 0`) and for unbilled rows (`NOT billed`); only a partition that holds neither is dropped. A partition still holding either is retained and surfaced as *blocked* — `UncreditedEarnRows`, `UnbilledRows`, `OldestUncredited` on the retention worker — instead of being deleted, and a lock the check cannot take is treated as blocked too (counts reported as `-1`). With the supplier chain enabled the barrier additionally reconciles each UTC source day (`earn > 0`, owner uid: Σcost / Σearn / row_count) against `supplier_reconciliation` and only flips the day to `closed` (with `closed_revision` / `closed_at`) before the DROP; a missing, extra, numerically mismatched or still-open day blocks the partition. Net effect: a deployment that accumulates unbilled usage rows now keeps those partitions on disk instead of dropping them by age — in particular with `billing.enabled = false` the settlement worker is not registered, so captured rows are never marked `billed` and *every* usage partition becomes permanently blocked — and freeing that disk needs the backlog to clear instead of waiting for the retention window to pass.

- **Enabling supplier earnings needs a fresh deployment (Beta, no migration path)**: the change adds a `supplier` value to the `users.role` enum, an `accounts.supplier_user_id` ownership column (NULL = platform-owned), three `usage_logs` earning columns (`supplier_user_id`, `supplier_earn_millis`, `supplier_credited`) with two partial indexes (`usagelog_uncredited_earn_id`, `usagelog_supplier_created_at`), and four new tables (`supplier_balances`, `supplier_frozen_chunks`, `supplier_settlements`, `supplier_reconciliation`, with a natural-key `UNIQUE` carrying `ON CONFLICT`). They are bootstrapped by ent / the partition bootstrap; a deployment must run that bootstrap before setting `supplier.enabled = true`. `supplier.enabled` ships `false`, so a deployment that never turns the chain on keeps today's routing, billing and billing-cursor behaviour — the retention barrier above is the one part in effect regardless.

- **Codex per-account identity is runtime-only and the account-ext contract is trimmed**: the persisted `codex_identity` object now carries only `installation_id` — the retired `session_id` / `thread_id` / `window_id` (which the response already always reported as `null`) are removed from the OpenAPI schema, the generated Go/TS types and the console read-only panel. Runtime identity is owned by the scheduler's slot pool instead of being stored per account, so nothing is lost; only clients that read those three fields are affected.

### Added

- **API keys can switch routing group**: the user console's key list now shows the group **name** (falling back to `#<id>` for a retired group) and lets a key move to another group in place from the list, or from a group dropdown in the edit dialog. Only groups the user could already pick when creating a key are selectable (public, or granted private). `PUT /api/user/keys/{id}` accepts an optional `group_id`, re-checks eligibility before writing, and refreshes the key's auth snapshot with the target group's protocol-convert set so routing switches immediately. Key read responses now include `GroupName` (empty when the group is soft-deleted).

- **Balance change history for admins**: permanent balance changes that are not usage-based (signup default balance, admin-created user, admin adjustment, redemption) are now recorded row-by-row in a new `balance_logs` table, written in the same transaction as the balance change itself. A new `GET /api/admin/users/{id}/balance-logs` endpoint lists a user's records with pagination, and `/app/users` exposes them behind a per-row history button. Records cover the permanent balance only; usage-based spending stays in `usage_logs`. The table is unpartitioned and keeps rows indefinitely (low volume per user; no retention policy).

- **Management API keys (`mk-`)**: a self-service, owner-scoped credential for the management surfaces, independent of the existing client keys. A key authenticates as its owner's identity and reaches exactly the owner's role closure (`user` ⊂ `supplier` ⊂ `platform_admin`): a `user` key works on `/api/user/*`, a `supplier` key additionally on `/api/user/supplier/*`, and only a `platform_admin` key reaches `/api/admin/*`. The plaintext is `mk-` + 32 hex (35 chars), `Authorization: Bearer mk-...` is discriminated by prefix first, and a failed lookup never falls back to JWT; the owner snapshot is re-checked fail-closed (missing/inactive owner → 401, and a demotion is reflected live). Keys are managed from one page, `/user/management-keys`, reachable from the account menu on both desktop and mobile, backed by `GET`/`POST /api/user/management-keys` and `PUT`/`DELETE /api/user/management-keys/{id}`; any signed-in identity can use it, ownership is enforced (cross-owner → 404). Create returns the plaintext key, which is stored and always shown/copyable (the same self-hosting tradeoff as client keys); `PUT` sets the name and `status` (`active`/`disabled` — a disabled key is immediately 401 and can be re-enabled); delete is soft and drops the key from the running instance's snapshot at once, with cross-instance convergence via NOTIFY.

- **Supplier role and account ownership**: a third user role `supplier` joins `platform_admin` / `user` in the `UserRole` enum, so the admin user surface can read and write it and the console can type it. Accounts gain an owner: `accounts.supplier_user_id` identifies the supplier that owns an account, `NULL` meaning platform-owned. The admin account write surface accepts `supplier_user_id` (a positive id assigns/transfers ownership, explicit `null` clears it back to platform-owned); the target must be an active user with supplier-surface access, re-checked under a `users` row lock inside the same write transaction, sharing that lock with the disable path to remove the transfer/disable race. Ownership is a ledger attribute only and does not advance `identity_revision`, so a transfer or credential refresh does not invalidate an in-flight routing plan. Accounts with an owner are held out of scheduling until the finance snapshot is ready, so a not-yet-loaded ownership is never silently billed as platform revenue; platform-owned accounts are unaffected.

- **Supplier earnings data plane, config and finance view**: a new `[supplier]` config section (`enabled`, `freeze_enabled`, `freeze_hours`, `thaw_granularity`, `share_bp_default`, `payout_max_backlog_rows`, `payout_max_backlog_age`, `payout_max_observe_age`, `risk_review_max_age`) is validated fail-fast at startup with a dedicated validator that is not folded into the shared duration/int tables: `thaw_granularity` must be `>= 1m` and a whole number of seconds, `share_bp` must be in `[0, 10000]` (`1000` = 10%; `0` is valid), and `freeze_hours >= 0` is checked against the cross-field ceiling `ceil(freeze_hours*3600 / thaw_granularity) + 1 <= 64` with an overflow guard before the multiply. `supplier.enabled` gates the whole chain (workers, view, new rows entering the earning index, and the supplier surface; the four tables still exist with zero rows). On the proxy hot path `finish` now stamps the three `usage_logs` earning columns once billing is done, using a single-pointer finance view (`SupplierSnapshot` / `SupplierView`, one atomic load for a consistent snapshot) exposed as three-state observability (`loaded` / `last_success` / `stale_age`). The share is computed with exact integer division — `earn_millis = floor(cost_millis * share_bp / 10000)`, no clamp anywhere, negative cost yields `0` — and the credited cursor is born in its terminal state (`credited = earn <= 0`), so with the chain disabled every row is zeroed and `credited = true` and never enters the earning index. The view is reloaded locally on an ownership/enable write so the old ownership stops being selectable before the new one takes effect.

- **Supplier credit and thaw chains run as real workers**: credit (frozen → available) and thaw chains are persisted with real SQL and wired at startup. Batches are picked over the consumption index, frozen per `freeze_hours` (per-supplier override, else the global default resolved from config for `NULL`), and credited in one transaction (chunk upsert → per-uid pre-locked balances in uid order → row accumulation → source-day reconciliation upsert → `usage_logs` marking) with balance-override and marking-count guards and an amount-conservation check. Thaw runs as its own ordered four-step chain (`DELETE ... RETURNING` → pre-lock → `UPDATE` + override guard), and with `freeze_enabled = false` earnings go straight to `available` while existing frozen buckets drain. The `main` wiring registers the `supplier-view` / `supplier-credit` / `supplier-thaw` workers in the order thaw → credit → reconciliation and drains them in reverse, gives `Close` its own total budget (per-round limited release so a frozen bucket left by a disabled freeze is still drained), retries `40P01` / `55P03` a bounded number of times, holds a leader session lock for batch pickup, and validates the per-supplier override set at startup (an out-of-range override refuses startup and lists the uid).

- **Supplier business endpoints and settlement application**: a new supplier surface is mounted at `/api/user/supplier/*` for the roles `supplier` and `platform_admin`, only when `supplier.enabled = true`. It exposes `GET /overview` (available / frozen / lifetime credited / lifetime paid / effective `share_bp` and `freeze_hours` / latest thaw time / bucket row count), `GET /earnings` (paged interval detail over the report index), `GET /chunks` (frozen buckets), `GET /settlements` and `POST /settlements`. Applying for settlement is one transaction (explicit `READ COMMITTED`) that conditionally deducts `available` (`available >= amount`), extends the period chain (`MAX(period_end)` in its own statement, `clock_timestamp`, `GREATEST`), and is idempotent on `request_key`: the key is pre-checked before deducting, a concurrent same-key insert uniquely conflicts and rolls back to read the original, and the same key with different parameters answers **409**. The account subset on the same surface (accounts full set plus read-only groups and templates) is served by reusing the admin handlers, so the field-level contract is identical.

- **Admin settlement review, payout claiming and owner balances**: administrators can now approve and pay out settlements and inspect/adjust owner balances — previously money reached `available` with no way out. The surface adds `GET /api/admin/supplier/settlements` (filter by `status` / `kind`) and the five-state CAS transitions `pending → approved → paying → paid`, with `reject` (only from `pending` / `approved`) refunding `available`, `confirm-failed` returning `paying → approved` and `paid` accumulating `lifetime_paid`. Claiming a payout fixes the full external side-effect protocol before any money moves: `claim` must carry the amount (equal to the statement amount, else **400**), a structured payee snapshot (`payee_name` / `account` / `unit`, fixed on first claim and reused on retry — a different target is rejected), a structured risk record (`reference` / `summary` / `approved_revision`, where `approved_revision` must equal the current approved revision and the server derives `operator_id` / `decided_at` / `scope` / `decision` / `expires_at`; unknown keys, wrong types, missing fields, a future `decided_at`, an over-long/expired `expires_at` and a tampered revision are all rejected), and a globally unique `payment_key` that is generated on first claim and permanently reused so a retry can never pay a different account. `paid` requires a non-empty `external_ref` (bank/channel receipt number), and `confirm-failed` requires the structured "confirmed not paid" verdict with the stopped-old-execution confirmation. `admin-request` reuses the same conditional-deduct and period-chain channel (recording the administrator as requester) and needs the target to already have a balance row. Every funds command requires a *named* JWT operator: the write transaction locks the operator's `users` row and re-checks `status` / `role` / `token_version`, so a stale or demoted credential is refused, and the static admin management token is rejected with **403** by an outermost funds gate (it would otherwise be short-circuited to 401 by the JWT check before reaching the handler).

- **Supplier console and a reused accounts page**: suppliers previously had backend endpoints but no UI. The console adds an overview (claimable / frozen / accrued / share rate / freeze period), earnings detail, frozen buckets, and settlement statements with an apply-for-settlement action carrying a stable `request_key` idempotency key. The accounts page is one component shared by `/app/accounts` and the supplier console, switching only its API base by scope (`/api/admin` ↔ `/api/user/supplier`): the admin surface gains the owner-supplier field while the supplier surface hides it (the server pins to the caller). The admin surface also gains a settlement workbench — a list plus five-state CAS approval (approve / reject-and-refund / claim payment / confirm paid / confirm-failed rollback), apply-on-behalf, and a supplier-balance list with per-supplier config (share rate and freeze period only). The accounts page now states that accounts without an assigned group take no traffic. Two statistics reads outside the supplier route subset (stats capabilities and account trend) are turned off under supplier scope instead of returning a guaranteed 404; account usage aggregation still uses the allowed `/accounts/usage`.

- **Supplier account surface generated from the API contract**: the supplier account/group/template subset is no longer a hand-maintained second route set. Its 17 paths are registered explicitly in the OpenAPI document under the `supplier` tag and the routes are code-generated from that contract (`tag` is the boundary and the single source of truth): the request bodies / responses / query parameters reuse the existing components (the admin list and usage parameters are hoisted into shared `components.parameters`), so a field-level addition can no longer be silently missing on one face. At runtime the generated handlers are mounted and forward to the existing admin wrappers (same handlers, same field validation), which turns default-deny structural — only `supplier`-tagged operations are registered, and the hand-written allow-list and guards are gone.

- **Group descriptions shown with the multiplier in group pickers**: groups gain an optional `description` maintained in the admin create/edit dialog and shown as a new list column (empty shows `—`). The user-side key group pickers (create dropdown, edit dropdown, and the in-place group-switch popover) now show each group's description (when non-empty) next to its price multiplier (`×N` / free / `—`), through a shared `GroupOptionMeta` component that also deduplicates the two earlier formatters. `description` is threaded through domain / ent / repo / service / handler / openapi; it is a non-empty column defaulting to `""` (existing rows migrate to the empty string, no destructive migration) and is nullable-optional on the request (POST omitted/null = empty, PUT omitted/null = keep, `""` = clear).

- **Users list filtered by role (and by supplier surface)**: `GET /api/admin/users` gains optional `role` (exact; an unknown non-empty value returns an empty list, lenient) and `supplier_surface` (only supplier-reachable roles — `supplier` / `platform_admin` from the single source of truth `domain.SupplierSurfaceRoles`); `supplier_surface` overrides `role`. Both are applied before the count, so `total` and the rows share the same filter, and omitting either keeps the existing behaviour. The users page gains a matching role dropdown (all / platform admin / user / supplier) mapping that parameter — "all" omits it and every other choice filters by that role (the parameter previously had no frontend consumer). The role filter combines with the email filter, and changing either resets to the first page; the toolbar's clear button clears only the email and keeps the role, while the empty-result "reset" clears both.

- **Codex accounts now serve from a per-account identity slot pool**: each Codex account holds `K = max_concurrency` lock-free slots (`internal/scheduler/identity_pool.go`). A claim is a rotating cursor plus a per-slot CAS and a release is a plain store — no channel, no mutex and no per-request lock on the request path — and the pool registry is republished with copy-modify-store exactly like the scheduler's static view. Concurrent requests on one account therefore present **distinct** thread/window identities upstream while sharing one `installation_id`, so upstream sees several independent sessions rather than one. Identity is injected at dispatch from the claimed slot and advanced (`window` / `thread`) only when usage is observed; a reload or a capacity change rebuilds the pool by position (an unchanged pool is reused verbatim, preserving in-flight `busy` flags and slot identity, a busy slot is not migrated), and the pool is capped at 1024 slots so a pathological `max_concurrency` cannot allocate unbounded state.

- **`[codex_identity]` rotation settings**: `wmax_lo` / `wmax_hi` / `scope` (defaults `2` / `6` / `total`) control how many windows a thread may keep alive — sampled uniformly from `[wmax_lo, wmax_hi]` when a thread opens, with `wmax_hi = 0` meaning never retire — and the water-level basis (`total` is the Codex default; `body_after_prefix` counts only growth after the window start). Startup fails fast when `1 > wmax_lo`, when `wmax_lo > wmax_hi` (unless `wmax_hi = 0`) or on an unknown scope.

- **Async continuation binding for Responses REST streams**: a new `cont-bind` worker (a `worker.Worker` and `StatsProvider`, registered in the managed worker set) drains a bounded queue in batches and persists bindings through the new `continuation.Store.CreateOrRefreshBatch`, which runs one Redis pipeline `Exec` per batch with the same validation, key and CAS payload as the synchronous path and reports per-item `created` / `refreshed` / `conflict` alongside per-item I/O and encoding errors (a pipeline-level outage fails the whole batch). The stream mapper now exposes the bindable response id explicitly instead of a caller re-parsing mapped frames. The worker's `queued` / `queue_cap` / `bound` / `dropped` / `failed` / `conflicts` / `unattributed` counters surface through `GET /api/admin/ops/workers`, documented in the OpenAPI contract and the console.

- **Unified SSE downlink owner with keepalive**: `pkg/sserelay.Output` is now the single downlink owner for all six streaming surfaces (responses, chat, anthropic, converted, images and Codex images). It holds the real wire, its own write buffer, the one serial lock and the commit state (`committed` / `businessSent` / `writeFailed`), and is responsible for full-frame writes, batch flush, silent keepalive (a successful visible write reschedules it; the line is always `: keepalive\n`), cancelling the upstream context when a heartbeat write fails (returning the saved I/O error first) and refusing writes after `Finish`. A new `proxy.stream_keepalive_interval` (default `10s`, `0` disables the generic heartbeat) drives it; the Codex images synthesis path keeps its SDK-driven 60s heartbeat and the images wire comment is normalised to `: keepalive\n`.

- **Helm chart for Kubernetes**: a new `deploy/helm/` chart deploys the c3api gateway only — PostgreSQL and Redis are not bundled and must be external. Connection info is `externalDatabase.dsn` / `externalRedis.addr`, or an `existingSecret` that takes precedence (at least one of each pair is required, otherwise rendering fails via `required`); the JWT secret (`auth-jwt-secret`, required) comes from a chart-managed Secret (`secrets.create`, default on) or an external one. `config.content` defaults to `server = { addr = ":18080", time_zone = "" }` + `scheduler = { default_max_concurrency = 8 }`, and the chart always injects `C3API_SERVER_ADDR=":<app.port>"` so both the config-file and env-only (`config.inline=false`) modes listen on the same port as the Service and the probes; the README lists the full default config. The pod runs non-root (uid 10001) with a read-only root filesystem plus a `/tmp` `emptyDir`, dropped capabilities and a `RuntimeDefault` seccomp profile, three `/healthz` probes (a ~120 s `startup` probe covering first-boot bootstrap), `terminationGracePeriodSeconds: 60`, and a rolling strategy of `maxUnavailable: 0` / `maxSurge: 1`. Ingress and the PodDisruptionBudget are off by default; because a PDB with one replica would block all voluntary evictions, enabling `podDisruptionBudget` while the effective minimum replicas is `1` now fails at render time. Hardening: a Secret checksum annotation rolls the pod when the secret changes, empty `app.env` values are skipped while non-string scalars such as `0`/`false` are kept, ingress `path`/`pathType` are quoted, `revisionHistoryLimit`/`minReadySeconds` and a `helm test` connectivity smoke are included, and the Deployment sets `enableServiceLinks: false` — Kubernetes otherwise injects `<service>_`-prefixed variables for every Service in the namespace, and because the app parses every `C3API_`-prefixed variable as configuration, a release or service name starting with `c3api` fed it bogus keys (`port`, `service`, `18080_tcp*`), so the process exited at boot.

- **Optional HorizontalPodAutoscaler**: a new `autoscaling` block (disabled by default) renders an `autoscaling/v2` HPA and makes the Deployment omit its `replicas` field so the HPA owns scaling. CPU and memory targets (percent of requests, default `80`/`80`) are configurable, and the PodDisruptionBudget minimum-replica guard keys off the effective minimum — `replicaCount`, or `autoscaling.minReplicas` when autoscaling is enabled.

- **Low-balance users' concurrency is clamped from config**: two new `proxy` keys — `low_balance_max_concurrency` (default `5`) and `low_balance_threshold_usd` (default `10`) — cap a user's user-level concurrency to the configured value while their permanent balance is strictly below the threshold, restoring the original cap once the balance returns above it. `low_balance_max_concurrency = 0` disables the feature (bit-for-bit the previous behaviour). It is folded into the existing balance pre-check as a single snapshot read plus an integer compare, so the hot path gains no allocation (a benchmark asserts the enabled and disabled paths allocate equally). The feature ships **on** by default, so a user whose balance is below $10 is clamped to 5 immediately after upgrade if their old cap was larger; validation rejects a negative cap and requires a positive threshold only when the cap is positive.

- **Routing plans can be filtered to the observed flow window**: `GET /api/admin/routing/plan` gains an optional paired `observed_from` / `observed_to`; when given, `routes` keeps only routes that have `routing_flow_fact` records in the half-open window `[from, to)`, while `route` bypasses the window filter and supplying only one bound is a **400**. The response adds `plan_total_routes` so a caller can tell "empty plan" from "no traffic in this window" (the plain `total_routes` remains the post-filter count). The read is a single range scan over `terminal_minute` reusing the `routing_flow_fact_uniq` index — no DDL or index change.

- **Thaw, credit and retention health are reported to ops**: the thaw chain now reports its bucket lag, overdue rows and amount, a rolling 5-minute successful-deletion rate and a recovery ETA; a failed credit refresh marks the lag stale (rather than leaving the last healthy value to be read as fresh); and the retention worker keeps a persistent `blocked`-partition alert (the partitions the retirement barrier refused to `DROP`, plus the first-blocked time and the oldest uncredited amount) and adds a data-disk view with free bytes and an exhaustion ETA. When free space on the data volume drops below the floor (default 5 GiB), retention flips a gate that refuses **new supplier ingress** for supplier-owned accounts; platform-owned accounts are unaffected, because platform supply does not depend on the supplier disk budget.

### Changed

- **`proxy.behind_cdn` now defaults to `true`**: the client IP column (usage and error logs) trusts `CF-Connecting-IP` → `True-Client-IP` → `X-Real-IP` (first non-empty) with a `RemoteAddr` fallback, instead of the previous `RemoteAddr`-only default. Deployments that expose the gateway directly to the internet must set it back to `false`, because those headers are then client-forgeable.

- **PostgreSQL integration tests clone a template database per test**: the suite runs through `scripts/test.sh`, which builds one migrated template database and clones a private database from it (`CREATE DATABASE ... TEMPLATE`) for each test. Migrations now run once instead of ~20×, and because tests no longer share a schema the package binaries can run concurrently again — the old `go test -p 1` serialisation is gone. The script also enforces the repo's no-`t.Parallel()` discipline and pre-checks that the test role can create databases.

- **pgtest rebuilds an empty or half-built template instead of reusing it**: `internal/testsupport/pgtest` now marks a template ready with a database `COMMENT` (`pgtest:template-ready`) as the last step of a successful build, and reuses it only when the name exists *and* that marker is present and correct. A template left empty or half-migrated by a killed build (SIGKILL, a cancelled CI job, a crash) is now detected and rebuilt rather than mistaken for a fresh one — previously a stale empty template under the current source hash made every run fail with `relation "users" does not exist`. An unmarked override template (`C3API_TEST_TEMPLATE`) is likewise rebuilt unless it carries the marker. This supersedes the earlier "an existing template is reused without reading inside it" behaviour.

- **codex-sdk updated to `f79e2ac`**: `StreamBody` returns the raw streaming response body (only `200` is accepted; any other status — including `3xx` — and redirects are not followed, the body is read to completion and closed, and the status is returned as an error). Codex responses now stream through the shared raw-body relay instead of re-framing SDK payloads, so verbatim passthrough, keepalive, async continuation binding and pre-write usage/TTFT sampling apply to the Codex path as they do to the native Responses path.

- **A Responses REST stream is no longer hidden until its continuation binding lands** (behaviour change, deliberate): the old ACK-before-visible gate held every byte until the first response id was bound in Redis, so a slow upstream could emit zero bytes to the client and trip CDN read timeouts. Business frames now reach the writer immediately, and the first valid id frame is snapshotted (dispatch and request meta as of that moment) and enqueued **once per stream** at the pre-write seam — the native mapper is wrapped so the native and converted paths snapshot at the same point. Binding is now best-effort and batched: a Redis outage or a full queue is only counted, never rewritten into the in-flight response, while a lookup of `previous_response_id` still fails closed. The WebSocket face keeps its synchronous ACK-before-visible gate and non-streaming Responses keep the synchronous bind.

- **A supplier with outstanding funds refuses to shut down, and disabling a supplier cascades**: flipping `supplier.enabled` back to `false` used to leave frozen buckets, claimable balances and in-flight settlements permanently stranded. Startup now fails when `enabled = false` and any of — frozen buckets, uncredited usage rows, non-zero `available`, or payable settlements — is non-zero, printing the size of each item so the operator sees what is at stake. Disabling a user cascades to disabling the accounts it owns in the same transaction, and shares the `users`-row lock with the ownership-write path so the two cannot interleave.

- **The role gate is snapshot-based and fail-closed**: `RequireRole` now decides from the same in-memory user snapshot as `RequireJWT` / `adminAuth` (snapshot role must be in the allowed set; a missing or non-`active` snapshot is refused), instead of trusting a JWT claim, so a role demotion takes effect after the next successful auth-sync refresh. The supplier surface mounts through `RequireJWT` → `RequireRole(supplier|platform_admin)` → scope injection → allow-list. The function previously had no production caller, so existing surfaces are unchanged.

- **The default `proxy.max_body_size` is raised from 4 MiB to 64 MiB** (the code default and both shipped templates): the previous default of `4 << 20` was too small for the vision base64 payloads the comment already called out, so a larger request was rejected with a 413-class error. A deployment that wants the old ceiling must set `proxy.max_body_size` explicitly.

- **A zero account balance now blocks model requests**: the balance pre-check previously rejected only a negative or missing balance and let a balance of exactly `0` through, so under postpaid billing a `0`-balance account could still emit one request and overdraw. It now rejects `0` or negative with **402**, so an account with balance `0` and no temporary credit is stopped at the pre-check. The pre-check does not read temporary credit, so an account whose only funds are temporary credit is likewise blocked; free users/groups (effective multiplier `0`) are unaffected.

- **The routing flow selector lists only routes with traffic in the window**: the console's Stats → Routing flow route dropdown now sends the paired `observed_from` / `observed_to` (computed from the selected range, omitting both bounds — never a half-window — when the range is missing or outside `(0, 90d]`) and offers only routes that had traffic in it, telling "empty plan" from "no traffic in this window" via `plan_total_routes`. The user's selected route stays selected even when it leaves the window's traffic set; the selector falls back to the first route only on first load or when the selected route has left the plan, and the count badge uses the full-plan `total_routes`.

- **The web console is now type-safe**: translation resources moved from JSON to `as const` TS modules with i18next's type augmentation, so `t()` keys and interpolation variables are checked at compile time; dynamic-key escape hatches are confined to genuinely runtime-composed keys, and a locales sentinel test enforces that the `en` and `zh` key sets match and that key dynamic keys are not dropped. TypeScript `strict` is enabled in `tsconfig.app.json`, and the errors it surfaced are fixed (notably the `Select` wrapper narrowing Base UI's `Value | null` callback and null/undefined guards on the account, log, key, and temporary-balance forms).

### Fixed

- **Codex raw-body relay hardening**: an upstream `2xx` that is not `200` (201/204/206) is normalised to `502` before it reaches the pipeline instead of passing through as a `4xx`; `StreamBody` no longer follows redirects (a `3xx` is treated as non-200); and TTFT is sampled only on a real payload, so a comment/control frame or the terminating `[DONE]` no longer counts as the first token. Converted Codex responses no longer create a continuation binding for an id the client cannot consume — only the direct Codex / Responses path enqueues.

- **Stream error frames are encoded per client protocol**: the unified error frame used to be `data: {"message":…}`, which the OpenAI Go SSE decoder ignores, so a truncated committed stream was silently read as a normal end (`Stream.Err() == nil`). Errors are now written in the client's own shape — OpenAI (`event: error` plus top-level `{"error":{"message":…,"type":"server_error"}}`) or Anthropic (`{"type":"error","error":{"type":"api_error","message":…}}`) — across all six call sites, with the exit classification unchanged.

- **Keepalive and downlink accounting are error-aware**: a flush that fails after a successful write now marks the downlink failed and cancels the upstream context; every failed `bufio` write path settles the sent bytes, so already-delivered business bytes never stay counted as pending and frame bytes never count as business; the converted Codex terminal frame is emitted inside the relay lifecycle (before the write-deadline watcher stops), so a half-open client can still unblock by cancel or timeout; typed images now send the generic keepalive while the Codex images synthesis path deliberately does not; and usage/TTFT sampled before an uncommitted exit is carried into the final observation instead of being reported empty.

- **Codex Responses usage is read from `response.usage`**: the SDK now only recognises `response.output_item.done` and `response.completed.response.usage`, so streaming billing reads usage from `response.usage` rather than a top-level `usage` that now decodes to an empty object (the separate synthesised top-level `usage` for the non-streaming body stays independent); the un-prefixed event names and the top-level `usage` fallback are gone. Cache writes are read from `*_tokens_details.cache_write_tokens` (Chat `prompt_tokens_details`, Responses `input_tokens_details`) instead of the Anthropic `cache_creation.ephemeral_5m/1h_input_tokens` fields, which are always `0` on Responses — so cache-write volume is now actually billed.

- **Cache writes are charged once and survive protocol conversion**: Responses/Chat `input_tokens` are gross (cache write ⊆ input), so net billable input is now `input − cache_read − cache_write` with cache-read and cache-write each on their own rate (a negative is treated as absent, and a pathological `cr + cc > it` clamps to zero) — previously cache writes were charged at both the input rate and the cache-write rate. Protocol conversion pins one gross-InputTokens convention (`resp→mess` emits net, `mess→resp`/`chat` rebuild gross), so a `resp→mess→resp` round trip is conserved and idempotent instead of inflating `input_tokens`; cache-write mapping is added in all three directions (`resp↔mess`, `resp↔chat`, `mess↔chat`, streaming and non-streaming), omitting zero-valued keys.

- **Identity pool publication and release are ordered correctly**: the slot pools are now published with the static view at the same point — a raised `max_concurrency` or a newly added Codex account no longer leaves the gate ahead of the pool (which previously meant missing injection, per-request ephemeral-identity fallback warnings, or leaked pools on deletion), and `InvalidateGroup` maintains pools too. A slot is now freed **before** the concurrency count is decremented, so a freshly admitted request never falls back to an ephemeral identity while a slot is logically free.

- **Codex HTTP client cache is bounded**: the multi-entry `HTTPClient` cache was keyed by an identity signature that includes the thread/window, so identity rotation grew it without bound; it is now an LRU capped at `codexHTTPClientCacheMax` that rebuilds only the evicted entry.

- **Converted requests that land on a Codex account go through the SDK adapter**: a protocol-converted request (chat→responses, messages→responses) that selected a Codex account previously used the generic client and failed with `unsupported protocol scheme ""` (Codex templates carry no base URL); it now routes through the Codex SDK adapter and maps the Responses output back to the client protocol.

- **Account ownership scope is enforced inside the SQL, closing several TOCTOU holes**: the supplier surface scope (`domain.AccountScope`, carried through the request context) is pushed down so that listing, single read, single write, delete, batch, ext, recover and usage each AND an ownership predicate into the query — a cross-owner id answers **404** rather than fetching the row first and comparing in the app layer. This covers the ext read/write path (owner predicate via a correlated subquery / `SELECT ... FOR UPDATE` inside the write transaction), the account usage aggregation (a cross-owner id is rejected before aggregation; the Codex ext read in scope never reads another supplier's credential or probes upstream), and the Codex import dedup/CAS (dedup and credential rotation are constrained to the current owner; cross-owner same-key collides on the global unique index and is reported as a row failure with no other id echoed in the message).

- **Creating an account as admin no longer drops the requested supplier, and writes cannot revive a disabled supplier's accounts**: admin create now projects `supplier_user_id` through the same patch validation (previously it was parsed then ignored, so the account became platform-owned while bypassing the target-user check), and batch writes that carry no ownership change still verify that every account's current and final owner stays supplier-reachable and `active`. Create / enable / transfer share one lock protocol that locks the full current ∪ target ∪ discovered owner `users` rows by ascending uid first and the account rows second (restart-on-discovery keeps it monotonic), removing the previous `accounts → users` / `users → accounts` deadlock window.

- **Settlement and funds commands are fail-closed**: rejecting a settlement now requires the `available` refund `UPDATE` to hit exactly one row — if the balance row is missing the whole transaction rolls back instead of committing a rejected statement with no refund (matching the paid-side guard). The supplier-surface funds commands reject the static admin management token with **403** explicitly.

- **Payout claiming is hardened against double or misdirected payment**: a claim must present the full side-effect protocol before it can leave `approved` (amount matching the statement, structured payee snapshot, structured risk record), `paid` requires a non-empty `external_ref`, `confirm-failed` requires the structured not-paid + old-execution-stopped confirmation (an unknown state fails closed and keeps `paying`), and the risk record is strictly deserialized (unknown keys, wrong types, missing fields, future `decided_at`, over-long/expired `expires_at`, tampered `operator_id` / `scope` / `revision` are rejected) on the real claim request.

- **Credit/thaw chain correctness under failure**: thaw aggregates are asserted before the balance `UPDATE` (non-negative uid/amount, `AddChecked` overflow, equal-length arrays, non-negative deltas) so fault injection cannot produce an out-of-bounds write; with `freeze_enabled = false` the credit `Close` now drains existing frozen buckets each round before returning, so a shutdown cannot strand frozen funds (which previously could even refuse the next `enabled = false` startup check); and the credit/thaw consume alerts keep their distinct per-stage event names (fetch / freeze-hours / apply, plus drain variants) so event-name-keyed alerting stays filterable.

- **Source-day reconciliation is closed before a partition is dropped**: partition retirement now first aggregates the partition by `earn > 0`, owner uid and UTC source day and `FULL JOIN`s it against `supplier_reconciliation`, atomically writing `state = 'closed'` with `closed_revision` / `closed_at` (the affected row count must equal the number of source-day keys to close) only when they agree; otherwise the partition is blocked and retained.

- **Supplier earnings workers and the finance view are visible to ops**: the `credit` / `thaw` / `view` components returned concrete snapshot types, so the ops assembly's type assertion silently skipped them and `/api/admin/ops/workers` never showed the supplier earnings chain. They now expose a uniform `Stats() any`; the finance-view loader joins the ops candidates and a `supplier-view` snapshot is registered, so a loader that has never succeeded (earnings stuck at zero) is visible as a NotReady snapshot error while the loader keeps serving the previous view.

- **The Redis client honours per-command context deadlines**: `pkg/redisx.Open` used the default `redis.Options`, so go-redis v9 ignored per-command context deadlines and the I/O bound degraded to `ReadTimeout` (5 s) times the default retries — the intended "2 s per Redis batch" budget and the existing `contOpTimeout = 2s` were not actually enforced, so a stalled connection could hold a worker far longer than intended. `ContextTimeoutEnabled` is now enabled so each command's context deadline applies, with explicit `ReadTimeout`/`WriteTimeout` (the go-redis default 5 s) as the fallback for commands that carry no deadline. The `Open` signature, the Ping semantics and the error text are unchanged.

- **The routing flow selector stays readable across window edge cases**: the route select is now uncontrolled (matching the logs filter), so the selected route name stays visible — including a kept selection that has left the window's traffic set; the count badge falls back to the full-plan count when no window was sent instead of falsely claiming "in window", and is hidden for an empty plan; changing the range keeps the previous frame's data so the badge/generation no longer flashes to zero; and a truncation hint is shown when the window-traffic routes exceed the selector's cap.

- **Long group descriptions wrap instead of clipping**: a long (especially CJK) description was hard-clipped on one line in the `Select` dropdown and overflowed past the popover's right edge with no ellipsis; the description now wraps via an explicit `whitespace-normal` on the shared group-option meta, while the group name stays single-line-truncated so the multiplier stays right-aligned and the row height stays even. The in-place group-switch popover was widened (`w-48` → `w-80`) for multi-line content.

- **Group descriptions keep their line breaks**: a description supports `\n` (native textarea), but the display collapsed it to spaces; the description line is now `whitespace-pre-line`, and the admin group list's description column is `pre-line` with `line-clamp-2` so a long description does not stretch the row.

- **Ops console supplier earnings metrics are localized**: the supplier earnings workers (`supplier-credit` / `thaw` / `view`), the credit-lag fields, the thaw bucket / overdue / rate / recovery-ETA metrics, the view-load counts, and the retention `blocked` and disk-capacity fields previously rendered as raw English identifiers and now have paired EN/ZH strings.

## [v0.0.1-beta.7] - 2026-09-28

### Breaking

- **Routing cost is an input-side unit price, not spend per success**: compiled account order and `GET /api/admin/routing/frontier` now returns `input_unit_cost` instead of `cost_per_success`. Both the compiled account order and this field use milli-cents per million input-side tokens. Cache reads pull it down and a lower account multiplier pulls it down. Output tokens and prompt length no longer move an account ahead of another. A zero input-side total is unknown cost.

- **Six statistics reads now take either an absolute range or a relative `window`, never a silent "today" default**: `GET /api/admin/stats/trend`, `/stats/entity-trend`, `/stats/ttft`, `/api/admin/accounts/usage`, `/api/user/stats` and `/api/user/stats/ttft` no longer require `from` and `to`. A request must give exactly one form — both bounds, or `window` alone (`24h`, `168h`, `2160h`; anything `time.ParseDuration` accepts). Giving both forms, only one bound, or neither is **400** `reason=window_ambiguous`. `window=7d` is **400** `reason=window_invalid`: a calendar day is not an hour-grid length, and a DST day is not 24h. Account usage no longer treats a missing range as "today in the request timezone". The console presets (the account-usage ranges, the default last-24h on both statistics pages, and the user overview's last 7 days) now send `window=` so the server, which owns the clock, builds an hour-aligned window; a range the user picks by hand still sends absolute `from` and `to`. Usage logs, error logs, `/stats/top`, routing reads and `/overview` are not in this break — their `from`/`to` (or `days`) stay required and they do not accept `window`.

- **Routing observation storage is bounded and the read window is guarded (Beta, fresh deployment required)**: the per-minute flow instance layer is gone and the flow data is now a single merged table, so `/routing/flow` edges now carry `min_generation` (the earliest plan generation folded into that edge) instead of `generation` plus `candidate_fingerprint`, and the response replaces the `stale_chains` / `total_chains` ratio with the exact boolean `stale_generation_present`. A new `[routing] observation_retention_days` setting (default `7`, floor `2`, startup fails below the floor) decouples observation retention from the 180-day usage-stats retention, and both `/routing/flow` and `/routing/frontier` now reject a window that starts before the retention cutoff with **HTTP 400** instead of silently returning a partial aggregation — callers that asked for more than the configured retention depth must page within it. The `routing-rollup` worker is gone, together with the per-minute instance/rollup quality tables, the dirty bits and the rollup watermark: quality snapshots now land directly in the single `routing_quality_fact` table, which is the only quality store.

- **Account usage aggregation now refuses spans longer than 90 days**: `GET /api/admin/accounts/usage` computes its totals with a whole-range `GROUP BY` and no `LIMIT`, so with partition retention disabled a single request could scan the entire table. The span is now capped at 90 days (the same limit the statistics trend face uses) and a longer request answers 400 instead of running — the console's per-account usage dialog no longer offers a 90-day preset on deployments whose log retention is shorter than that, because the request behind it could not be served.

- **Raw-row grouped statistics now have a fixed 8-day window limit instead of one derived from retention**: when a timezone cannot use the pre-aggregated table (a `:30`/`:45` offset, or a window crossing a DST transition), statistics group `usage_logs` + `err_logs` rows directly. That window limit used to be computed from the configured retention, so keeping more logs *widened* the scan a single request was allowed to run — the cost direction was backwards (scanning ten days of logs costs the same however long logs are kept). It is now a constant 8 days. Deployments keeping more than 7 days of logs therefore see a half-hour-offset or DST-crossing request for more than 8 days flip from 200 to 400; the default deployment is unchanged, because 8 days was already the documented promise.

- **AI routes live only under `/v1/*`**: the gateway no longer mounts the proxy on `/`. A request to `/chat/completions` (or any other AI path without the `/v1` prefix) is no longer served by the proxy.

- **Account writes are one patch, fenced by two different generations**: create, single update and batch update share one field set (lifecycle, cost multiplier, cache domain, Codex import included). A single update takes `lifecycle_revision` as its compare-and-swap token. Routing and health use a separate `identity_revision`, which does not move when only a credential is refreshed, so an in-flight plan stays valid across that refresh. Setting an account cost multiplier to `0` is kept; it is no longer replaced by the create default.

- **Four raw-log read paths now reject a window that starts before the retention cutoff instead of silently returning partial data**: `/api/admin/usage_logs`, `/api/user/usage_logs`, `/api/admin/err_logs`, `/api/user/err_logs`, `/api/admin/accounts/usage`, and the entity-level branch of `/api/admin/stats/ttft`. Their rows live in daily partitions that the retention worker `DROP`s, so a window starting earlier could never be completed — the answer was silently smaller than the request. Measured on a deployment keeping two days of logs: a 30-day `/usage_logs` request returned exactly the same 151 rows as a 2-day one, and entity-level TTFT reported a sample count of 3 for a 7-day window. These now answer 400 with a machine-readable reason, so a caller that wants older data must page within the retention window rather than being shown a truncated answer as if it were complete.

### Changed

- **The partition-retention worker now reports whether it is actually keeping the routing tables bounded**: `GET /api/admin/ops/workers` gains, on the `retention` worker, `partition_count` / `oldest_partition_unix_ms` over the routing fact tables, plus the per-table diagnostics `quality_partition_count` / `quality_oldest_partition_unix_ms` and `flow_partition_count` / `flow_oldest_partition_unix_ms` (one table failing its `DROP` shows up in the aggregate only as drift, so the per-table pair is what names the faulty table), the progress pair `last_dropped_routing_quality_partitions` / `last_dropped_routing_flow_partitions`, `snapshot_state_rows` (the handover-state table is not partitioned, so a failing `DELETE` grows it without limit), `undated_partition_count` (partitions whose name carries no date — they are neither counted nor dropped, so they need a human), `partition_stats_stale` (this round's query failed, so the values shown are the previous round's), and `routing_observation_retention_days` (the cutoff the oldest-partition value should be read against). That worker also warns when the oldest routing partition is older than the cutoff. The routing observation tables stay bounded only while this worker runs; if it stops or its `DROP` keeps failing, they grow without limit and nothing else notices, so these values are the signal. In a healthy system the oldest partition is never older than the cutoff, which is what makes the warning meaningful rather than noise.
- **Routing observability is paginated and folded, so all three read endpoints now answer one page instead of the whole collection (behaviour change, deliberate)**: `GET /api/admin/routing/plan|flow|frontier` gained `offset`/`limit` (default `0`/`20`, cap `200` on all three), plus a second per-route candidate axis (`candidates_offset`/`candidates_limit`) on `/routing/plan` and a per-layer top-N account fold (`accounts`, default 20) on `/routing/flow`. Every one of the three therefore returns less than before for callers that do not page: `/routing/flow` returns 20 edge rows where it returned all of them, `/routing/frontier` returns 20 candidates where it returned 200, and `/routing/plan` returns the first 20 routes where it returned the entire plan — the last being the sharpest change, since that endpoint previously took no parameters at all and was a complete enumeration. To see everything, page with `offset`/`limit` until the response's own count is reached (`total_edges`, `total_candidates`, `total_routes`); passing `limit=200` alone is not complete above 200 rows. `/routing/plan` also gained `search` (case-insensitive substring over model / format / operation tag / group id) and `route` (exact, takes precedence over `search`), so a single route can be fetched directly instead of paged to. Paging never changes meaning: `first_dispatch_chains`, `terminal_chains`, `total_edges`, `stale_generation_present`, `total_candidates`, `total_routes` and the Sankey graph are all computed over the complete set before the page is sliced, and folding separately preserves each layer's chain count — so the first-dispatch/terminal conservation check still holds and the graph does not distort. The old-generation badge is no longer derived in the browser: the server answers an exact boolean `stale_generation_present` (the window contains an edge row whose `min_generation` differs from `plan_generation`) and the console shows or hides the badge from it, so the badge no longer flickers while paging. The chain-weighted ratio (`stale_chains` / `total_chains`) this entry first described was retired in the same unreleased cycle: once the flow layers merged, one row aggregates the chains of several generations, so such a ratio could only be an upper bound — and an exact per-generation split is not storable, because the "current generation" is a moving target.
- **Client request headers now reach upstream on the raw, typed and responses-WS faces (behaviour change, deliberate)**: everything not on the deny list is relayed verbatim — custom and session-style headers (for example `X-Opencode-Session`, `X-Claude-Code-Session-Id`, `Session-Id`), plus client-reported protocol headers such as `Anthropic-Version` and `OpenAI-Beta` (a client's own protocol declaration may override the SDK/gateway default). The three faces share one mechanism (a single deny list in `pkg/aiclient/relay.go`, not configurable); the codex WebSocket face is deliberately the opposite — it forwards no client header at all (see below).
- **Stripped on the way out, everywhere**: connection-level hop-by-hop headers (`Connection`, `Upgrade`, `Te`, `Trailer`, `Keep-Alive`, `Proxy-*`, `Sec-WebSocket-*`), entity-level headers describing a body the gateway may rewrite (`Content-Length`, `Content-Type`, `Content-Encoding`, `Transfer-Encoding`), `Host`, credential and cross-tenant carriers (`Authorization`, `X-Api-Key`, `Cookie`), and `Accept-Encoding` (billing guard: relaying a client's `gzip` makes upstream return a compressed body that usage extraction and model rewriting would silently read as plain JSON). Also stripped: client-IP and forwarding-path headers (`X-Forwarded-For`, `X-Real-IP`, `CF-Connecting-IP`, `True-Client-IP`, `Forwarded`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Forwarded-Port`, `Via` — they describe the client's own connection while upstream sees the gateway as its peer, and the gateway appends no observation of its own), `Expect: 100-continue` (a negotiation about the client's connection to the gateway; relaying it made every request to an upstream that never sends an interim `100 Continue` pay the transport's `ExpectContinueTimeout`, a client-injectable delay), and `X-Request-Id` (written by the gateway itself — the client's value when supplied, otherwise a generated UUID — so forwarding it either leaked the internal correlation id or let a client inject an unvalidated value; note it is not the same id stored in usage logs). This is deliberately **not** a security boundary: the list is a deny list, so other keys carrying the same kind of information (for example `X-Client-IP`, or any custom header) still reach upstream.
- **The Codex WebSocket face now forwards no client headers at all**: previously it relayed every client header surviving the shared deny list except a seven-item disguise list, so custom headers such as `X-Opencode-Session` and `X-Client-Version` did reach upstream, and a client `User-Agent` or `Originator` could override the disguised identity. That face now sends only what the SDK writes for it — disguise identity, beta value, session family and credential — so upstream always sees the SDK's disguise values and no client header can influence the handshake it sees.
- **Header values containing CR, LF, NUL, DEL or other control bytes are dropped per value** instead of being allowed to fail the entire upstream request.

- **Statistics responses now state which window was actually read**: `GET /api/admin/stats/trend`, `GET /api/admin/stats/entity-trend` and `GET /api/user/stats` answer with a bare array, so the window and the storage used travel in response headers (`X-Stats-Effective-From`, `X-Stats-Effective-To`, `X-Stats-Storage`) rather than in the body. A window whose bounds are not on whole hours is normalised *forward* to the next hour when that makes the pre-aggregated table usable, so the effective window can start (and end) later than the one requested — which is exactly what the headers are for. `/api/admin/overview` deliberately has no such header: its window is derived from local day boundaries and never shifts.

- **Statistics rejections now carry machine-readable fields**: a 400 body from a statistics endpoint gains optional `reason` (`window_invalid`, `window_too_long`, `raw_horizon`, `cube_horizon`), `storage`, `limit_seconds`, `effective_from`, `effective_to` and `retention_days` next to the existing human-readable `error` string. Every added field is optional, so existing clients are unaffected; fields that do not apply are omitted rather than defaulted (an invalid window reports no storage and no limit).

- **The console no longer second-guesses the server about statistics windows**: the client-side hour-alignment patch is gone (the server normalises and echoes the effective window), the range pickers and the TTFT window bound are derived from the new capabilities endpoint instead of hardcoded day counts, and a rejected request shows the window the server actually read next to the error message. Range presets that this deployment cannot serve are no longer offered at all.

The two are independent: the cost limit is a constant that does not move with retention, while coverage is per table and takes the most conservative table a shape reads. The endpoint is a mechanical projection of the same in-memory matrix the window guards use, so the numbers it reports cannot drift from the behaviour that enforces them. It reports only per-deployment constants — whether one particular request can use the pre-aggregated table depends on where its window sits, and that is reported per request by the headers above instead of being faked as a deployment constant.

### Breaking

- **Model mapping contract replaced (Beta, fresh deployment required)**: `model_mapping` changes from `map[string]string` to a strict object form `map[string]{mapped_model: string, mode: explicit|implicit}` (`required: [mapped_model, mode]`, `additionalProperties: false`, `mode` is only `explicit` or `implicit`, with no default; aliases and `mapped_model` are case-sensitive, and empty/whitespace/leading-or-trailing-blank values are rejected; an identity mapping is valid and keeps its `mode`; the canonical empty value is `{}`; omitting the field on `POST`/`PUT` equals `{}`, `PUT` replaces the whole mapping, and `batch-update` is tri-state: omitted = keep, object = full replace, `{}` = clear — never a per-row merge). Runtime identity matrix: no mapping = passthrough unchanged; `explicit` (identity included) keeps the current upstream target, pricing and passthrough behavior (with `MappedModel` empty for identity); `implicit` (identity included) still sends the mapping target upstream, but `UsageLog.Model` and `MappedModel` both record the client-requested model and pricing/precheck use the client model, while recognized response paths (`model` / `response.model` / `message.model` — only existing string values are rewritten, missing fields are never created; when several paths coexist all are rewritten; `[DONE]`, non-2xx, unrelated nesting, `null`, numbers, objects, arrays, malformed payloads, comments and opaque bytes are untouched) are rewritten to the client model; SSE rewrites frame by frame after `200`, WS after the accepted first frame, `Search` stays fully opaque, standard Images only rewrites the target of JSON requests, multipart is never rebuilt, and a response without a model field is not given one. The scheduler keeps a single map lookup and the existing routing / model-list / hard-whitelist / rule topology, there is no compatibility with the old form and no migration path, and upgrading needs a fresh deployment (old string or invalid object values fail loudly at load, initial load is fail-closed, runtime reload keeps the last valid snapshot).
- **API key quota is now a spend limit, not a token limit**: `quota` / `quota_used` are redefined as cumulative billed cost in milli-cents (1 USD = 100,000 milli-cents) and are deducted from the final cost after settlement. Existing rows keep their old numeric meaning (no backfill — Beta has no migration path), so keys must be re-created or re-set. Values are capped at 2^53-1 milli-cents so console arithmetic stays exact; larger (or negative) quotas now reject with 400. The quota writer is gated on billing — with billing disabled, quotas are not consumed.
- **Group RPM rate limiting removed**: the `group_key_rpm` setting and its fixed-window limiter are gone (no product tier used them). Requests are still gated by user/key concurrency, account concurrency and client-IP identification. Setting the key now fails at startup via the unknown-key check.
- **Codex accounts and templates can no longer carry an endpoint override**: `base_url` must be empty for any Codex-credential template or account (rejected by validation in the service and enforced transactionally in the repository, with the same rules applied to batch updates against the post-patch effective state). All Codex traffic — Responses over HTTP and WebSocket, Images and Search — now goes to the official SDK endpoints, and `AccountCredential` no longer carries a per-call `BaseURL`; the WebSocket URL override factory in the client layer is gone. The admin console disables those fields and explains why.
- **`billing.flush_workers` removed**: settlement uses a single adaptive executor; `usage.flush_workers` is unchanged. Configs still carrying the billing key fail at startup.
- **Balance warning emails are disabled by default**: the global toggle now ships off (previously on), so an upgrade sends nothing until a platform admin enables it; explicit settings still win.
- **`server.time_zone` must be nested, not top-level**: the shipped TOML templates showed it as a root key, and uncommenting it was correctly rejected as an invalid key. Both templates now use an inline `server` table with `time_zone = ""`.

### Added

- **Request-level timezone for statistics**: every stats surface (`/api/admin/overview`, `/stats/trend`, `/stats/entity-trend`, `/stats/top`, `/stats/ttft`, account usage aggregation and `/api/user/stats*`) accepts an optional `timezone` query parameter with an IANA name (the consoles send the browser zone). It only affects grouping: time buckets aggregate on that zone's local hour/day boundaries and the default "today" window uses its local midnight, while explicit `from`/`to` stay absolute and are passed through untouched; rankings and TTFT percentiles are timezone-independent. Trend and entity-trend queries route to the pre-aggregated cube when the zone aligns with storage and fall back to raw rows otherwise, and day buckets spanning more than the retention window answer 400 instead of silently truncating. Both admin and user statistics pages are localized, including per-key quota labels rendered in USD.
- **User balance warnings**: a user can set a USD threshold through the API (`0` disables). The warning fires when the permanent balance crosses that threshold after settlement — temporary credit never participates. Delivery is best-effort on the mail worker with a per-user, per-threshold 24 h cooldown; a generic SMTP channel test, a global admin toggle and the `balance_warning` templates ship with it.

### Changed

- **Lock-free upstream client lookups**: the client factory's global per-request mutex is replaced by a single atomic copy-on-write snapshot (template clients plus URL cache). Reads are pure atomic loads with immutable map lookups; writers build outside the lock and CAS-retry, and a generation counter preserves the previous full-invalidation ordering so a stale client can never be republished after invalidation. Concurrent lazy builds of different formats merge field by field instead of clobbering.
- **Settlement is fail-closed**: a failed batch no longer drains the cursor head without deducting. Failures return immediately and leave `usage_logs` rows unbilled for replay, concurrent-mark losses replay at most once, and the atomic pairing of deduction plus marking for successful rows is unchanged.
- **Usage log inserts are idempotent**: batches key conflict resolution on `(request_id, created_at)` and skip duplicates, so a commit-ambiguity replay can no longer double-write a partition, while unrelated unique-constraint violations still surface.
- **Notification consumers wait for the baseline**: instance subscription starts only after a full refresh succeeds; a failed refresh closes the connection and reconnects through the existing backoff path instead of applying deltas onto a stale snapshot.
- **Snapshot reload failures are contained**: each reload goroutine isolates panics, keeps sibling reloads running, and reports a sanitized stack with a one-shot diagnostic budget rather than crashing the process.
- **Stats reads preserve timezone-aware cube paths**; account usage aggregation now accepts fractional-hour boundaries.
